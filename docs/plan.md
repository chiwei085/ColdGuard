# 開發計畫

報告日：2026-12-16。

採一次實作到位的推進節奏：先奠定 sim-core、時間推進與虛擬裝置的模擬基底，再接入現成的 esp-emu，完成韌體閉環與三節點功能。完成即驗收，隨後進入展示打磨與報告準備。以下為開發目標，完成與否仍以驗收結果為準。

## 1. 模擬基底與接入驗證

先完成可獨立 headless 執行的模擬環境：sim-core 管理熱、電、門與故障狀態，以固定步長推進，支援暫停、重設、場景輸入與狀態快照。以預設的 relay 輸入驗證冷卻、開門升溫與斷電停止冷卻；相同初始狀態與輸入重跑，結果一致。

接著完成虛擬裝置與 coordinator 的連接介面，將溫度、電量、RFID 與 relay 對應至 I²C、UART、GPIO。此階段以測試輸入驅動設備訊號，控制決策仍留給後續韌體，sim-core 專注於物理狀態演進。

基底就緒後，直接接入現成的 esp-emu，以最小 C 韌體讀取 I²C 溫度、控制 relay GPIO，再加入 MQTT。S1–S3 以單節點驗收，S4 以三節點驗收：

| 編號 | 驗證項目 | 通過條件 |
|---|---|---|
| S1 | 暫停 | 停止 grant 30 s（真實時間），模擬時間不前進 |
| S2 | 閉環 | 溫度由虛擬裝置提供，relay 狀態回饋至熱模型 |
| S3 | 可重現 | 不接網路，同一場景執行 10 次，事件序列一致 |
| S4 | 三節點 | 三個實例同時持鐘並連線 MQTT，持續 10 分鐘無 deadlock；記錄速度比 |

S4 要求速度比 ≥ 1×。不足時依序嘗試 ESP32-C3、較大的 quantum（先確認 #71 不會發生）。S1–S3 無法通過時，改用真實時間 1×、不做 lockstep，虛擬裝置沿用。

## 2. 驗收項目

S1–S4 見第 1 節。

| 項目 | 驗收場景 |
|---|---|
| B1 物理模型 | sim-core 以固定步長 headless 執行；以預設 relay 輸入跑通冷卻、開門與斷電，輸出狀態快照 |
| B2 場景重播 | 支援暫停、重設、場景輸入與故障注入；同一初始狀態與輸入重跑，物理狀態序列一致 |
| B3 虛擬裝置與協調介面 | 依第 3 節落實腳位表、匯流排位址、暫存器與訊框格式；以測試請求驗證 I²C 溫度、電量、RFID 與 GPIO relay 映射，備妥 coordinator 的時間發放介面 |
| B4 三節點協作 | 依第 3 節落實 MQTT schema，接入 Mosquitto；三節點同時運作，狀態與心跳可追蹤 |
| F1 冰箱監控 | 門開超過 60 s、溫度越界、冷卻失效、凍結，各自觸發正確警報 |
| F2 庫存 | 首次有效越界讀值即將受影響批次標為 Do Not Use；回溫不自動解鎖，複核前拒絕出庫；進出庫記錄時間與人員，事件持久化 |
| F3 電力 | 市電中斷後冷卻停止，電池維持監控；估計安全時間，達門檻即建議轉運 |
| F4 轉運 | 冷藏箱溫度或電量不合格時拒絕出發；在途持續監控；出發與到達皆有交接記錄 |
| F5 容錯 | 連續遺失 3 次心跳（約 15 s）標為離線，並拒絕無法確認的批次；復線後補傳記錄 |
| D1 視覺化 | 依第 4 節建置診所、三節點、可識別批次、隔離標示、備援供電及交接區；物件位置、設備讀值與操作結果對應實際狀態 |
| D2 劇本重播 | 依第 4 節重播正常營運、斷電轉運與失聯復線主線，另驗證越界隔離及出發拒絕分支；畫面、批次流向與事件記錄一致 |
| D3 展示版 | D1、D2 整合通過；預設視角可辨識三節點，關鍵操作有提示與回饋，搬運與交接可見，重設後回到一致的初始場景 |

## 3. 設定與依據

採用下列設定直接開發。冷鏈處置參考 CDC 指引，感測介面依元件資料表；沒有通用標準的控制、電量與通訊門檻，明列為本專案的工程預設並納入驗收。情境限定為需 2–8 °C 冷藏的疫苗。物理、取樣與業務門檻採模擬時間；MQTT 心跳與重送在 1× 展示下驗收，網路場景不快轉。

### 冷鏈與控制

| 項目 | 採用設定 | 依據 |
|---|---|---|
| 安全範圍與目標 | 安全範圍 2–8 °C，控制目標 5 °C；使用帶熱慣性的 glycol 探頭溫度判定 | CDC 建議冷藏範圍與緩衝探頭；5 °C 為範圍中點 [5] |
| 越界與批次鎖定 | 每 1 s 取樣；首次有效讀值 < 2 °C 或 > 8 °C 即警報，將當時位於該儲存單元的批次標為 Do Not Use，記錄起訖、極值與持續時間。回到安全範圍仍維持鎖定，須記錄人員與判定依據才能解鎖 | CDC 要求隔離越界疫苗並諮詢製造商或主管單位；未提供通用的安全越界時長。1 s 為專案取樣設定 [6] |
| 凍結風險 | 有效讀值 ≤ 0 °C 立即高優先警報並停止冷卻；讀值無效或感測器失聯時另報感測故障，拒絕出庫 | 0 °C 為本專案的風險警報門檻，並非所有疫苗的實際凍結點 |
| 冷卻遲滯 | ≥ 5.5 °C 開啟、≤ 4.5 °C 關閉，中間維持原狀；relay 初始關閉 | 圍繞 5 °C 的工程預設，以正常場景確認不頻繁切換且保持 2–8 °C |
| 冷卻失效 | 市電正常、門關閉且冷卻持續開啟 300 s，探頭降溫不足 0.2 °C 時警報；條件中斷即重算觀察窗 | 工程預設；以正常冷卻與冷卻能力歸零兩個場景驗收，獨立於越界警報 |
| 門未關 | 開門超過 60 s 警報 | 本專案的工程預設 |

### 電力與轉運

CDC 建議預先建立緊急移轉流程，依儲存設備表現與備援條件處理斷電 [1]。電量百分比無法單獨保證安全，以下以預估可用時間決策；時間裕量均為專案設定。

| 項目 | 採用設定 |
|---|---|
| 備援電力 | 冰箱斷市電後冷卻停止，電池僅供監控與通訊。電池模型以容量 Wh 與負載 W 計算剩餘時間；低電量 ≤ 20% 警告、≤ 10% 升級緊急警報 |
| 安全時間估計 | 韌體依最近 60 s 有效溫度估計升溫斜率，以抵達 8 °C 的時間與監控剩餘供電時間取較小值；斜率無法可靠估計時顯示未知並建議準備轉運。越界時安全時間為 0；不把模型預測當成批次放行依據 |
| 轉運觸發 | 預估安全時間 ≤ 預計裝箱與轉運時間 + 15 min 即建議轉運；基準劇本設裝箱 5 min、路程 15 min，因此在剩餘 ≤ 35 min 時觸發 |
| 出發條件 | 冷藏箱有效溫度連續 5 min 維持 2–8 °C；電量 ≥ 20%，且監控供電與箱體保冷預估均可涵蓋裝箱、路程與 15 min 裕量；接收端已確認可收貨。任一條件未知或不符即拒絕出發 |
| 箱體保冷 | 基準冷藏箱採被動保冷，電池供監控；可用保冷時間取自該箱型正常／高環溫場景的驗證結果。出發前依目前箱溫與環溫選用較保守結果，溫度全程監控 |
| 交接 | 出發與到達記錄批次、人員、時間、溫度及箱號；到達後先檢查完整溫度與交接記錄，待確認前拒絕出庫 |

### 裝置、通訊與記錄

| 項目 | 採用設定與依據 |
|---|---|
| ESP32-S3 腳位 | 各節點採相同對照：I²C SDA=GPIO8、SCL=GPIO9；relay=GPIO4（高電位啟動）、門磁=GPIO5（上拉，低電位為關門）、市電存在=GPIO6（高有效）、蜂鳴器=GPIO7（高有效）；RFID UART1 TX=GPIO17、RX=GPIO18。依 ESP32-S3 GPIO matrix 選腳，避開啟動、flash／PSRAM 與 USB 腳；未使用的裝置不接入 [2] |
| 溫度介面 | 採 TMP117 暫存器介面，I²C 100 kHz、7-bit 位址 0x48；溫度暫存器 0x00，16-bit 二補數、MSB first，每 LSB 為 0.0078125 °C；就緒前讀值不作有效溫度。實作所需的設定與狀態暫存器行為依資料表 [3] |
| 電量介面 | 專案虛擬 I²C 裝置 0x36，暫存器 0x00 回傳 uint16 電量（0–10000，單位 0.01%）、0x02 回傳 uint16 電池電壓（mV），皆 MSB first；這是自訂介面，不宣稱相容特定電量計 |
| RFID 訊框 | 沿用架構的簡化 UART 讀取器，9600 baud、8N1；每框為 STX 0x02、8 個 ASCII hex UID 字元、2 個 ASCII hex XOR 校驗字元、ETX 0x03。校驗值為 UID 解碼後 4 bytes 的 XOR；錯誤框丟棄並記錄。此為專案格式 |
| MQTT topic | `coldguard/v1/{node_id}/{telemetry,heartbeat,event,command,ack}`；node_id 固定為 fridge、carrier、inventory。遙測每 1 s、心跳每 5 s；失去 3 次心跳標離線。事件／命令／ACK 採 QoS 1，命令不 retained；QoS 1 可能重複，接收端須去重 [4] |
| MQTT payload | JSON envelope 含 `version`、`node_id`、`boot_id`、`seq`、`sim_time_ms`、`type`、`body`、`checksum`。body 為緊湊 JSON 的 UTF-8 字串，checksum 採該字串 bytes 的 CRC-32/ISO-HDLC；數值附固定單位，body 另含批次／人員等事件欄位。用 `(node_id, boot_id, seq)` 去重 |
| 事件確認與補傳 | 先寫節點持久記錄再發布；接收端持久寫入後才回 application ACK，引用來源 boot_id 與 seq。未收到 ACK 每 5 s 重送，離線保留，復線依序補傳；重複事件只 ACK、不重複執行。MQTT PUBACK 不代替應用層完成確認 [4] |
| 持久化與容量 | 節點採 flash 追加記錄，至少 4096 筆、每筆上限 256 bytes，預留 1 MiB 資料空間及額外 metadata 空間；每 60 s 保存含 min/max 的摘要，異常與交接立即保存，另保留最近 60 s 的 1 Hz RAM 樣本供異常時上傳。主機用 SQLite 儲存節點實際上報資料，保留至少 3 年並可匯出；3 年參考 CDC [5]，不代表保存每秒完整歷史 |
| 容量耗盡 | 已由主機持久保存並 ACK 的記錄可回收，未 ACK 的關鍵事件不得覆寫；預留 1024 筆供關鍵事件，容量不足先停一般摘要並警報，關鍵區耗盡時拒絕出庫及新轉運。主機資料庫預留 2 GiB 起始空間，隨資料量擴充；不宣稱固定空間可涵蓋任意事件量 |
| 工作切分 | 依模擬核心／虛擬裝置與協調／韌體與通訊／場景與驗收切分工作，以本節介面銜接；實際人員指派由組內安排，不作為技術設定的前置條件 |

## 4. 故事與場景設計

場景呈現一間小型診所的人員如何保存、領用及保護疫苗。觀眾應能從設備、藥盒位置、標示與操作回饋理解目前發生什麼事，以及人員為何採取下一個動作。以下均為建置目標，完成與否由 D1–D3 驗收，不代表目前已實作。

### 空間與必要元素

診所包含冷藏儲存區、庫存操作區、裝箱區與通往接收端的轉運動線。冰箱門打開後不遮住讀卡機或裝箱區，冷藏箱開蓋後能看見冰袋、探頭與批次。接收端以獨立地點標示與交接區呈現，沿用三節點架構，不另增加韌體節點或顯示未接入設備的即時讀值。

| 區域／物件 | 必要元素與用途 |
|---|---|
| 疫苗冰箱 | 可開關的門、門磁、層架、疫苗批次、glycol 緩衝探頭與線路。設備正面標示 2–8 °C 保存範圍，顯示數字溫度、冷卻、市電／電池、網路與警報狀態 |
| 疫苗批次 | 每批有獨立物件、可讀批號與 RFID 標籤，批號和庫存終端一致。可用一個藥盒或托盤代表一批，不以大量無識別的裝飾盒代替實際庫存 |
| 冷藏隔離位置 | 冰箱內有標示的隔離籃或層位。受影響批次先在原位置加上 Do Not Use 標示，人員移至隔離位置後仍留在冷藏環境；回溫不自動移除標示 |
| 庫存終端 | 螢幕、RFID 讀取區與可辨識的員工證。區分人員識別和批次掃描，顯示批號、位置、狀態、操作結果及人員。複核時能查看越界紀錄並填寫判定依據 |
| 備援供電 | 可辨識的監控電池模組或電池艙、電源線與供電標示。清楚區分冷卻用市電和監控用電池，斷電時能看出冷卻停止而感測、記錄與警報持續 |
| 冷藏箱與裝箱區 | 可開關的箱蓋、冰袋、溫度探頭、電池／記錄器、可讀箱號及批次放置位置。顯示箱溫、電量、出發條件與在途狀態，裝箱前不預放與庫存無關的疫苗 |
| 出發與接收區 | 明確的離場方向、接收地點、交接位置及可用的 RFID 掃描位置。呈現出發與到達逐批掃描、人員確認及等待接收，能辨識哪批仍在箱內 |

### 故事主線與可見結果

主線在疫苗仍可安全轉運時完成裝箱。越界隔離另作分支，避免為了展示搬運而先放行已鎖定的批次。門、溫度、電量與時間門檻沿用第 3 節。

| 階段 | 人員／環境事件 | 場景應呈現的結果 |
|---|---|---|
| 正常營運 | 人員識別後逐批掃描入庫，並領用其中一批 | 對應批次進入冰箱或離開庫存，終端與實體位置一致，顯示時間與人員 |
| 門未關 | 取放疫苗後門持續開啟超過 60 s，再由人員關門 | 門角度對應實際開關狀態，設備發出可辨識的門警報，關門後反映警報解除。此段參數須能在未造成越界前展示門警報 |
| 市電中斷 | 冰箱失去市電 | 冷卻與非必要照明停止，監控由電池維持，顯示電量、安全時間或未知，以及保持關門提示 |
| 準備轉運 | 系統建議轉運，人員確認接收端並檢查冷藏箱 | 顯示箱溫、電量、穩定時間與可用時間是否合格。缺少條件時明列拒絕原因，不顯示已出發 |
| 裝箱與出發 | 人員逐批掃描，將可轉運批次放入合格冷藏箱，關蓋後確認出發 | 同一批次從冰箱移到箱內，更新位置與交接紀錄。整箱沿動線離開原位置，標示在途並持續顯示監控資料 |
| 途中失聯 | 轉運期間中斷網路，並嘗試領用無法確認的批次 | 顯示失聯與最後更新時間，遠端讀值不再假裝持續更新。箱端仍呈現本地監控與記錄，終端明確拒絕無法確認的領用 |
| 抵達與復線 | 冷藏箱到達接收區，恢復連線，逐批掃描交接 | 箱體出現在接收位置，顯示待確認批次、出發／抵達人員與時間、離櫃時長及溫度紀錄。補傳有進度或完成回饋，接收確認前維持禁止領用 |

另有三組可獨立重播的分支：

| 分支 | 場景應呈現的結果 |
|---|---|
| 越界與複核 | 受影響批次出現 Do Not Use 標示並留在冷藏環境，領用被拒絕。溫度恢復後仍鎖定，查看紀錄並記錄人員與依據後才更新為放行或報廢。報廢不顯示成正常領用 |
| 冷卻失效與凍結 | 分別呈現冷卻運轉但無有效降溫，以及凍結高優先警報與停止冷卻。警報有文字或圖示區別，不只共用一種紅燈 |
| 出發條件不合格 | 分別展示箱溫不合格、電量不足及接收端未確認。操作後箱體留在原地，批次不進入在途狀態，畫面顯示對應原因 |

### 模型與狀態連動

房間、櫃體及裝飾可為靜態模型。批次、門蓋、電源指示、警報標示及交接物件須能獨立控制：

- 每個批次以穩定識別對應庫存紀錄，提供儲存層位、隔離位置、箱內位置與交接位置。初始物件數量、批號及位置由初始庫存決定。
- 冷藏箱有共同父節點，箱體、箱蓋、監控器與已裝載批次隨整箱移動，箱蓋仍能獨立開合。搬運時不得穿過冰箱、檯面或櫃體。
- 物件命名與狀態綁定須可追蹤到設備或批次，不以匯出工具自動產生的流水號判定業務身分。
- 位置、交接與鎖定結果以系統確認狀態為準。等待回覆時顯示處理中，拒絕時維持原狀，不先播放成功搬運或自動放行。
- Bevy 只呈現快照與事件，不自行判定批次是否安全。搬運插值只改善視覺，不改變交接時間、庫存位置或韌體決策。
- 遠端最後已知狀態與本地仍在運作的設備須有區別。失聯、無效讀值與關機分別標示，不以正常綠燈或舊讀值冒充目前狀態。
- 暫停時門蓋、搬運及在途進度停止，重設時清除舊場景的批次標示、交接狀態與未完成動畫，還原一致的初始配置。

### 視角、操作與驗收條件

| 驗收面向 | 通過條件 |
|---|---|
| 預設構圖 | 在預設 1600 × 900 視窗可辨識冰箱、冷藏箱與終端，主要狀態不被介面遮擋。靠近或切換視角後能讀取批號、箱號及設備資訊 |
| 操作辨識 | 門、箱蓋、讀卡機及終端在指向時有輪廓或提示，點擊後有回饋。讀卡結果區分人員與批次，不能只靠快捷鍵或口頭解說理解 |
| 警報與供電 | 警報同時有文字／圖示及顏色，能區分門未關、越界、凍結、感測故障、斷電與失聯。電池百分比與供電來源可見，未知安全時間不顯示成零或安全 |
| 批次一致性 | 同一批號不會同時存在冰箱與冷藏箱兩處，入庫、領用、隔離、裝箱及接收後的物件位置與紀錄一致，Do Not Use 不因關閉面板或回溫消失 |
| 轉運可見性 | 從檢查、逐批裝箱、關蓋、出發、在途到接收都有對應畫面。拒絕出發不播放成功移動，接收前不顯示可領用 |
| 記錄可核對 | 可查看關鍵事件的模擬時間、人員、批號與箱號，核對畫面和交接紀錄。復線補傳不造成藥盒重複出現或交接重複執行 |
| 重播與分支 | D2 主線與各分支具有明確初始狀態、輸入、預期結果及結束條件，重設後可重新執行。網路段依第 3 節在 1× 驗證，不以動畫完成代替業務驗收 |
